2. Achados Críticos

Vulnerabilidades que devem ser corrigidas antes de qualquer deploy em produção.

CRÍTICO

C-01 · JWT e Refresh Token persistidos no localStorage

✓ CORRIGIDO

Arquivo: frontend/src/store/auth.ts

Impacto: Qualquer script XSS na página (extensão maliciosa, dependência comprometida, CDN injetado) consegue ler localStorage.getItem('archlab-auth') e obter o JWT + refresh token, efetivamente sequestrando a sessão do operador. Em um PDV com acesso a cancelamento de vendas e relatórios financeiros, isso é risco financeiro direto.

Evidência de código:

// ANTES — token e refreshToken gravados no localStorage
persist(
  (set) => ({ ... }),
  { name: 'archlab-auth' }   // padrão: localStorage — VULNERÁVEL
)
// DEPOIS — JWT excluído do persist; apenas metadata em sessionStorage
persist(
  (set) => ({ ... }),
  {
    name: 'archlab-auth',
    storage: sessionStorage,   // sessionStorage: fechado com a aba
    partialize: (state) => ({  // token NUNCA persiste
      refreshToken: state.refreshToken,
      username: state.username,
      role: state.role,
      isAuthenticated: state.isAuthenticated,
    }),
  }
)

Como reproduzir: Abrir DevTools → Application → Local Storage → archlab-auth. Token JWT e refresh token visíveis em plaintext.

Mitigação adicional futura: Mover refresh token para cookie HTTP-Only via endpoint /api/auth/cookie-login. O JWT continua só em memória.

CRÍTICO

C-02 · Security Headers ausentes no Archlab.Backend

✓ CORRIGIDO

Arquivo: Archlab.Backend/Program.cs

Impacto: Sem X-Frame-Options: DENY, a aplicação é vulnerável a clickjacking — um atacante pode embutir o PDV em um iframe invisível e capturar cliques do operador. Sem Content-Security-Policy, qualquer XSS pode carregar scripts externos. Sem X-Content-Type-Options, uploads com MIME errado podem ser executados pelo browser.

Evidência: Pdv.Backend/Program.cs tinha os headers; Archlab.Backend/Program.cs não tinha — drift entre as duas versões do backend.

// ADICIONADO em Archlab.Backend/Program.cs
app.Use(async (ctx, next) => {
    ctx.Response.Headers["X-Content-Type-Options"] = "nosniff";
    ctx.Response.Headers["X-Frame-Options"] = "DENY";
    ctx.Response.Headers["Referrer-Policy"] = "strict-origin-when-cross-origin";
    ctx.Response.Headers["Permissions-Policy"] = "geolocation=(), microphone=(), camera=()";
    ctx.Response.Headers["Content-Security-Policy"] =
        "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; " +
        "img-src 'self' data:; connect-src 'self'";
    await next();
});

3. Achados de Severidade Alta

ALTO

A-01 · Random.Shared não-criptográfico em chave de acesso fiscal

✓ CORRIGIDO

Arquivo: Archlab.Backend/Services/FiscalDocumentService.cs:BuildAccessKey()

Impacto: O campo random code de 8 dígitos na chave de acesso NFC-e era gerado com Random.Shared (PRNG determinístico, seed baseado em clock). Em sistemas com alta taxa de emissão, um atacante com acesso ao timestamp pode reduzir o espaço de busca em ordens de magnitude e forjar chaves de acesso fiscais válidas estruturalmente.

// ANTES
var randomCode = Random.Shared.Next(0, 99_999_999);

// DEPOIS — CSPRNG
var randomCode = RandomNumberGenerator.GetInt32(0, 99_999_999);
ALTO

A-02 · Cancelamento de venda acessível por qualquer operador autenticado

✓ CORRIGIDO

Arquivo: Archlab.Backend/Endpoints/SaleEndpoints.cs:45-51

Impacto: Qualquer usuário com role Operator podia cancelar qualquer venda, incluindo vendas de outros terminais e outras sessões. Isso representa risco de fraude interna (cancelamento pós-recebimento) e de quebra de controle financeiro.

// ANTES — apenas RequireAuthorization() genérico
group.MapPost("/{id:guid}/cancel", ...).WithName("CancelSale");

// DEPOIS — exige Admin ou Manager
group.MapPost("/{id:guid}/cancel", ...)
    .WithName("CancelSale")
    .RequireAuthorization("AdminOrManager");
ALTO

A-03 · Política de senha mínima insuficiente (8 chars, sem complexidade)

✓ CORRIGIDO

Arquivo: Archlab.Backend/Services/UserService.cs:CreateAsync, ChangePasswordAsync

Impacto: Senhas como abcdefg1 ou 12345678 eram aceitas. Em um sistema financeiro operado por múltiplos usuários, senhas fracas são o vetor mais comum de comprometimento de conta.

// ANTES — só comprimento
if (request.Password.Length < 8) return Fail("...");

// DEPOIS — comprimento + complexidade (NIST SP 800-63B-inspired)
private static string? ValidatePassword(string? password)
{
    if (password is null || password.Length < 12)
        return "Senha precisa ter no minimo 12 caracteres.";

    var hasUpper   = password.Any(char.IsUpper);
    var hasLower   = password.Any(char.IsLower);
    var hasDigit   = password.Any(char.IsDigit);
    var hasSpecial = password.Any(c => !char.IsLetterOrDigit(c));

    if (!hasUpper || !hasLower || !hasDigit || !hasSpecial)
        return "Senha precisa conter maiusculas, minusculas, numeros e caracteres especiais.";

    return null;
}

Nota: A senha de dev admin123 no appsettings.Development.json agora é rejeitada. Atualize o seed de dev.

ALTO

A-04 · Refresh token com lifetime de 30 dias

Arquivo: Archlab.Backend/Services/AuthService.cs:15

Impacto: Um refresh token comprometido garante 30 dias de acesso renovável sem nova autenticação. Para um PDV operado em múltiplos turnos, 7 dias é o máximo aceitável.

// ANTES
private static readonly TimeSpan RefreshTokenLifetime = TimeSpan.FromDays(30);

// SUGESTÃO
private static readonly TimeSpan RefreshTokenLifetime = TimeSpan.FromDays(7);

Status: Pendente — necessário ajuste manual.

ALTO

A-05 · Rate limiting global 100 req/min — login sem limite específico

Arquivo: Archlab.Backend/Program.cs:48-65

Impacto: Um atacante pode tentar 100 combinações de senha por minuto no endpoint /api/auth/login sem ser bloqueado além disso. Para senhas de 8 chars (antes da correção A-03), o espaço era pequeno o suficiente para ataque de dicionário online.

Correção sugerida:

// Adicionar política específica para auth endpoints
options.AddPolicy("auth-strict", httpContext =>
    RateLimitPartition.GetFixedWindowLimiter(
        httpContext.Connection.RemoteIpAddress?.ToString() ?? "anon",
        _ => new FixedWindowRateLimiterOptions
        {
            PermitLimit = 5,             // 5 tentativas de login por minuto por IP
            Window = TimeSpan.FromMinutes(1)
        }));

// Aplicar nos endpoints de login/refresh:
group.MapPost("/login", ...).RequireRateLimiting("auth-strict");
group.MapPost("/refresh", ...).RequireRateLimiting("auth-strict");

Status: Pendente — implementar na Semana 4.

Arquivo: Archlab.Backend/Domain/Customer.cs:Document, Sale.CustomerDocument

Impacto: Em caso de vazamento de banco, CPFs de clientes ficam expostos diretamente. A LGPD classifica CPF como dado pessoal sensível, e sua exposição pode gerar multa de até 2% do faturamento (máx R$50M por infração).

M-05 · HSTS sem configuração explícita no Archlab.Backend

✓ CORRIGIDO

Arquivo: Archlab.Backend/Program.cs

Impacto: O HSTS padrão do .NET usa max-age=30 (30 segundos!). Sem configuração explícita, browsers não bloqueam downgrade HTTPS→HTTP após reconexão. Adicionado MaxAge=365 dias + IncludeSubDomains.

5. Achados de Severidade Baixa

BAIXO

B-01 · OpenAPI disponível apenas em Development

O Scalar UI é mapeado apenas se IsDevelopment(). Para produção, considere uma rota separada com autenticação (ex.: /docs exigindo Admin) ou exportar o schema estático como artefato de CI.

BAIXO

B-02 · Sem API versioning

Todas as rotas usam /api/*. Sem versionamento (/api/v1/*), qualquer breaking change força atualização simultânea de todos os clientes. Recomendado adicionar antes do primeiro cliente externo.

BAIXO

B-03 · .env.example com valores de placeholder óbvios

POSTGRES_PASSWORD=change_me_strong_password e JWT_SECRET_KEY=change_me_at_least_32_chars_long_secret_key são placeholders que podem ser usados acidentalmente. Adicionar validação no startup que rejeite esses valores específicos em Production.

BAIXO

B-04 · appsettings.Development.json com JWT secret em VCS

"SecretKey": "dev-only-pdv-jwt-secret-key-minimo-256-bits-local" está commitado. Embora seja explicitamente dev, habilita ataques caso alguém confunda ambientes. Migrar para dotnet user-secrets ou variável de ambiente local.

BAIXO

B-05 · Nenhum mecanismo de limpeza de refresh tokens expirados

Tokens expirados ou revogados acumulam na tabela RefreshTokens. Com uso contínuo, a tabela crescerá ilimitadamente. Adicionar job de limpeza periódico (hosted service) ou trigger de DB.

BAIXO

B-06 · CI sem scanning de dependências vulneráveis

O pipeline .github/workflows/ci.yml faz build/test/docker mas não roda dotnet list package --vulnerable ou npm audit. Dependências comprometidas passariam direto para produção.

6. Análise Arquitetural

ALTO

Dois backends divergentes — maior risco arquitetural do projeto

O projeto mantém Pdv.Backend e Archlab.Backend simultaneamente. A divergência já causou o problema C-02 (headers de segurança presentes em um, ausentes no outro). Com o tempo:

  • Patches de segurança precisarão ser aplicados em dois lugares
  • Testes cobrem apenas Archlab — Pdv.Backend não tem testes
  • Migração de novos domínios (ex.: Category) está incompleta no Pdv.Backend
  • Desenvolvedores novos ficam confusos sobre qual é "o" backend

Recomendação: Deprecar Pdv.Backend formalmente (adicionar README de deprecação) e estabelecer Archlab.Backend como única fonte de verdade. Remover Pdv.Backend do CI e planejar remoção completa na Semana 6.

7. Performance & Escalabilidade

MÉDIO

P-01 · Groupings de relatórios faziam in-memory processing

✓ CORRIGIDO

GetTopProductsAsync carregava todos os SaleItems no período para o C# e agrupava em memória. Com 100k vendas/mês e 5 itens por venda = 500k objetos por request de relatório. Corrigido para grouping no SQL via EF Core.

// ANTES — 500k objetos em memória
var rows = await db.SaleItems.ToArrayAsync();
return rows.GroupBy(...).Select(...);

// DEPOIS — grouping no banco
return await db.SaleItems
    .GroupBy(i => new { i.ProductId, i.Barcode, i.ProductName })
    .Select(g => new TopProductEntry(...))
    .ToArrayAsync();

Nota: RevenueByDay mantém client-side apenas para DateOnly conversion — payload mínimo de 3 campos por venda.

BAIXO

P-02 · Sem índices explícitos em colunas de filtro críticas

O EF Core cria índices para FKs automaticamente, mas colunas de filtro frequente precisam de índice explícito:

P-03 · Sem paginação máxima por offset

Um usuário pode requisitar page=99999999&pageSize=100 causando OFFSET 9.999.999.900 no banco — query extremamente cara mesmo que retorne 0 registros. Adicionar limite de offset total.

9. Compliance LGPD & Fiscal

LGPD

CPF/CNPJ em plaintext — risco de multa e exposição de PII

CampoEntidadeRisco
DocumentCustomerCPF/CNPJ em plaintext no banco
CustomerDocumentSaleCPF em plaintext por venda
EmailCustomerDado pessoal, deve ser criptografado
PhoneCustomerDado pessoal, exposto em logs

Roadmap de correção:

  1. Curto prazo: mascarar na API response (***.000.000-**)
  2. Médio prazo: criptografia de coluna com chave gerenciada
  3. Longo prazo: hash para busca + encrypted blob para exibição
FISCAL

NFC-e simulada — não substitui emissão autorizada pela SEFAZ

O FiscalDocumentService gera documentos com estrutura de NFC-e mas sem:

  • Certificado digital A1/A3
  • Autorização da SEFAZ por webservice
  • Protocolo de autorização (nProt)
  • QR Code válido para consulta pública
  • Cálculos de impostos (ICMS, PIS, COFINS)

Usar em produção sem integração real é ilegal (Lei 87/96 e ATO COTEPE/ICMS 7/05). Planejar integração com provedor SAT/NFC-e na Semana 7-8.
