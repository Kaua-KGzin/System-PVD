SEMANA 1
Objetivo: Substituir o método perigoso EnsureCreated() por EF Core Migrations — a forma profissional de versionar o banco de dados. Sem isso, qualquer mudança no modelo apaga todos os dados em produção.
Passo a Passo
1
Instalar a ferramenta dotnet-ef
No terminal, execute uma vez (instalação global):
dotnet tool install --global dotnet-ef dotnet ef --version # confirme que funcionou
2
Ler os arquivos antes de modificar
Leia primeiro, altere depois. Entenda o que cada linha faz em:
Data/PdvDbContext.cs  |  Data/DatabaseSeeder.cs  |  Program.cs
3
Criar a primeira Migration
Dentro da pasta Pdv.Backend/:
cd Pdv.Backend dotnet ef migrations add InitialCreate
Isso cria a pasta Migrations/ com os métodos Up() (criar tabelas) e Down() (desfazer). Abra e leia o arquivo gerado!
4
Corrigir o DatabaseSeeder.cs
Encontre esta linha no arquivo e substitua:
// REMOVER isso: await context.Database.EnsureCreatedAsync(); // ADICIONAR isso: await context.Database.MigrateAsync();
Por quê? MigrateAsync() aplica todas as migrations em ordem. EnsureCreated() recria tudo do zero (destrói dados).
5
Deletar o banco antigo e testar
O pdv.db foi criado pelo método antigo — precisa ser deletado:
rm Pdv.Backend/pdv.db # apaga banco antigo dotnet run # recria via migration
Teste: acesse https://localhost:5235/health → deve retornar Healthy
6
Migration do User (aguardar Kauã)
Quando o Kauã criar o arquivo Domain/User.cs, você cria a migration:
dotnet ef migrations add AddUserEntity
⚠ Coordenem antes via chat. Quem cria a entidade, quem cria a migration. Nunca os dois ao mesmo tempo — gera conflito.
Dicas Importantes
💡
Erros do EF são descritivos. Leia a mensagem — ela diz exatamente o que falta.
🚫
Nunca edite arquivos dentro de Migrations/ na mão. Use migrations remove para desfazer.
📦
1 mudança no modelo = 1 migration nova com nome descritivo.
🔒
Git antes de tudo. Faça commit antes de qualquer mudança grande para ter um ponto de volta.
✅
Teste rodando o projeto. A melhor prova é o servidor subir sem erros.
